# 0004. Обработка ошибок: границы, узкие типы, без молчания

Статус: принято (02.11.2026)

## Контекст
В коде сервера 315 `except Exception` и 72 обработчика из одного `pass`.
Часть из них выдаёт баг за «СДО недоступно», одна пускала человека без
согласия при сбое базы (`middleware.py`, исправлено 02.11).

## Решение
- Широкий `except Exception` — только **на границе**: обработчик
  Telegram, HTTP-запрос, задание планировщика, фоновый цикл. Там ошибка
  пишется один раз **с traceback** (`logger.exception` / `exc_info=True`).
- Внутри — **узкие типы**: `httpx.HTTPError`, `sqlite3.Error`,
  `ValueError`, свои `SdoUnavailable`, `PayError`…
- «Не получилось — и ладно» допустимо для вспомогательного действия, но
  с записью в лог и комментарием, почему не страшно. С 03.11 это одна
  граница на весь код — `with aside(logger, "что делали"):`
  (`kapibara/core/errors.py`): сеть и отказ Telegram — строкой, баг — с
  traceback. Рассылка по людям, сообщение старосте, шаг после синка — так,
  а не своим `except Exception`.
- **Без молчания:** `except ...: pass` — только с узким типом и комментарием.
- Где проверка безопасности не удалась — **не пускаем** (fail closed).
- Три вида ошибок: виноват пользователь (понятный ответ), чужой сервис
  (ответ «недоступно» + warning), баг у нас (traceback, `/status`).

## Почему не иначе
Переписать всё разом опасно: сужение `except` может уронить сценарий,
где раньше ошибку тихо глотали. Поэтому сначала свет (лог вместо `pass`),
потом данные с живого сервера, потом сужение пачками по 10–15 мест.
