# ИИ-треды: модели, контекст и лимиты

Как устроена работа Claude в проекте, чтобы лимитов хватало дольше без потери
качества. Короткая выжимка — в [CLAUDE.md](../CLAUDE.md), раздел «Лимиты
Claude». Правила для ChatGPT и Antigravity (мосты на ПК Никиты) — в
инструкциях проекта.

## Коротко

1. **Платим за перечитывание.** Каждый шаг треда (каждый вызов инструмента)
   заново читает весь контекст треда. Расход ≈ размер контекста × число шагов ×
   цена модели.
2. **Тред — одна задача.** Маленький контекст, короткая жизнь, итог — в PR или
   файл.
3. **Модель — по роли** и на весь тред: смена модели сбрасывает кэш.
4. **Крупное — конвейером:** Opus планирует → Haiku или Sonnet исполняет →
   Opus проверяет результат, а не переписку.
5. **Толстый тред не будим** после паузы больше часа: начинаем новый с файлом
   передачи.
6. **Вывод инструментов — минимум.** Большие тексты — в файл, в чат — ссылка.

## 1. На что уходит лимит

Точную формулу лимитов подписки Anthropic не публикует. Для сравнения берём
цены API (ноябрь 2026); по наблюдениям, лимит ведёт себя так же: больше всего
съедает кэш.

| За миллион токенов | Opus 5.5 | Sonnet 5.5 | Haiku 5.5* |
|---|---|---|---|
| Вход без кэша | $4 | $2 | $0,10 |
| Чтение кэша | $0,20 | $0,10 | ≈$0,01 |
| Запись кэша на час (×2 к входу) | $8 | $4 | $0,20 |
| Выход (ответ и размышления) | $20 | $10 | $0,50 |

\* Пока запрос короче 100K токенов; длиннее — всё в 5 раз дороже.

Пример — тред, в контексте которого 150K токенов:

| Шаг | Opus 5.5 | Sonnet 5.5 |
|---|---|---|
| Тёплый: прошлый шаг был меньше часа назад | $0,03 | $0,015 |
| Холодный: пауза больше часа, весь контекст пишется заново по ×2 | $1,20 | $0,60 |
| 300 тёплых шагов — обычный длинный тред | $9 | $4,50 |

Что отсюда следует:

- **Холодный шаг в 40 раз дороже тёплого.** Толстый тред, который будят через
  часы или дни (ответ Никиты, мерж PR, таймер), каждый раз платит полную
  перезапись.
- **Длинный тред дорог числом шагов.** 300 шагов по 150K — это 45 млн токенов
  чтения кэша. Половина контекста — значит, вдвое дешевле каждый шаг.
- **Haiku в 40 раз дешевле Opus** и на вход, и на выход. Механическую работу по
  ясному плану выгодно отдавать ему, держа контекст до 100K.
- **Размышления — это выход,** самая дорогая строка. Усилие xhigh — там, где
  оно меняет результат.
- **У каждой модели свой кэш.** Смена модели посреди треда — перезапись всего
  контекста; смена усилия тоже может её вызвать. Модель и усилие задаём при
  старте.

## 2. Роли и модели

| Роль | Модель, усилие | Делает | Не делает |
|---|---|---|---|
| Координатор | Opus, medium | говорит с Никитой, ведёт план, запускает треды с моделью и ссылками на файлы | не читает код, логи и большие файлы, не исследует сам |
| Планировщик | Opus, xhigh | архитектура, план-файл для исполнителя, решения про право, деньги, безопасность | не исполняет план сам |
| Исполнитель | Haiku, high; Sonnet, high — где нужна смекалка (незнакомый код, UI, браузер) | идёт по плану, пишет код или отчёт, открывает PR | не меняет план и не угадывает: пишет «Неясно» |
| Проверяющий | Opus, high | читает план, диф и отчёт, сверяет выборочно, правит мелочи | не читает переписку исполнителя, не переделывает всё |
| Обычный тред | Sonnet, high | обычный PR, понятная правка, «веди за руку», сторы | — |
| Няня | Haiku, medium | CI, события PR, статусы, напоминания | сложное не чинит, зовёт Sonnet или Opus |

Fable — только по слову Никиты: нужны платные кредиты.

Помощники вне Claude (ChatGPT и Antigravity на ПК Никиты) — по инструкциям
проекта. У них просим сжатый ответ (диф, выводы, список), не целые файлы: их
ответ ложится в контекст Claude.

## 3. Какую схему брать

| Задача | Схема | Модели |
|---|---|---|
| Вопрос, статус, мелкая правка текста | один тред | Haiku или Sonnet, medium |
| Обычная правка кода, один PR, место понятное | один тред | Sonnet, high (Opus, medium — если место хитрое) |
| Большая работа по понятному плану: аудит, сбор фактов, переносы, массовые правки | конвейер (§4) | Opus xhigh → Haiku high → Opus high |
| «Почему не работает», архитектура, право, безопасность, деньги | планировщик, потом конвейер или один тред | Opus high–xhigh; на ПК — с ChatGPT |
| «Веди за руку»: сторы, сервер, касса, настройки | один короткий тред | Sonnet, medium–high |
| Дизайн | варианты → выбор Никиты → реализация → ревью | исполнение Sonnet, ревью Opus в свежем треде |
| Ждать CI или PR, статусы | лёгкий тред | Haiku |

Конвейер окупается, когда исполнение длинное: десятки файлов или шагов. Работу
меньше ~30 шагов дешевле сделать одним тредом.

## 4. Конвейер «план → исполнение → проверка»

1. **План — Opus, свежий тред.** Разбирается, принимает решения, пишет
   план-файл `/mnt/project-files/<тема>/plan.md` по шаблону ниже. Тред на этом
   заканчивается.
2. **Исполнение — Haiku или Sonnet, свежий контекст.** Отдельный тред от
   координатора или субагент (`Agent` с `model: haiku` или `sonnet`), если
   работа укладывается примерно в час: дольше — кэш ждущего Opus остынет.
   Исполнитель получает только путь к плану, пишет результат в файл после
   каждого блока, открывает и сопровождает PR (поздние события PR будят
   дешёвый тред, а не Opus).
3. **Проверка — Opus, свежий контекст.** Читает план и результат (диф PR,
   отчёт) по частям, выборочно сверяет 10–20% ссылок, правит мелочи в той же
   ветке до того, как PR назовут готовым, или даёт исполнителю второй круг
   списком.

Исполнитель дважды споткнулся на одном шаге — этот шаг (не всю работу) отдаём
Sonnet или Opus узким вопросом.

Образец — план сверки 152-ФЗ (`/mnt/project-files/legal/152fz-plan.md`).
Урок оттуда: отчёт вырос до ~265 КБ при задуманных 30–80 строках на блок.
Предел размера ставим жёстко, иначе проверка съедает то, что сэкономило
исполнение.

### Шаблон плана для ИИ

```markdown
# <Задача>: план для исполнителя

Дата, коммит `origin/main`. Исполнитель: <модель, усилие>. Проверяющий: <модель>.

## Цель и «готово»
Цель одной фразой. Готово, когда: <проверяемые признаки>.

## Правила исполнителя (читать первыми)
- Что можно менять и что нельзя (код, ветки, PR, файлы).
- Куда писать результат. Дописывать после каждого блока: если контекст
  сожмётся, сделанное уже в файле; при повторном старте — продолжить с
  первого незаписанного блока.
- Размер: блок — до N строк, весь отчёт — до 30 КБ.
- Только факты со ссылкой `файл:строка`; не понял — в «Неясно», не угадывать.
- Секреты не выписывать (только имена переменных).
- Когда остановиться и спросить.

## Блоки
### Б1. <название>
Смотреть: <пути, поиски `rg`>. Записать: <что и в каком виде>.
Готово, когда: <признак>.

## Для проверяющего
Что сверить целиком, что выборочно, какие решения принять, что показать Никите.
```

## 5. Жизнь треда

- **Старт.** Координатор даёт задачу, модель, усилие и ссылки на файлы (план,
  «где остановились»), а не пересказ переписки.
- **Модель и усилие — на весь тред.** Нужна другая модель — новый тред или
  субагент.
- **Конец.** Итог — в PR или файл, короткий ответ со ссылкой, тред закрыт.
  Продолжение через часы — новым тредом.
- **Пауза больше часа.** Если контекст больше ~100K, старый тред не будим:
  записываем файл передачи и начинаем новый. Маленький тред будить можно.
- **Постоянных тредов нет.** Тема (посты, релизы, фильм, ревью дизайна) живёт в
  файле `/mnt/project-files/<тема>/ГДЕ-ОСТАНОВИЛИСЬ.md` (образец —
  `promo/film/GDE-OSTANOVILIS.md`), каждый заход — свежий тред с этим файлом.
  Знание тредов-экспертов (концепция нового дизайна) — в файле или `docs/`,
  чтобы ревью мог сделать свежий тред.
- **Ожидание.** Проверки по таймеру — с растущим интервалом и в лёгком треде.

Файл передачи — до 3 КБ:

```markdown
# <Тема>: где остановились
Обновлено: <дата>, <тред>.
Цель: …
Сделано: … (PR, файлы)
Решения Никиты: …
Дальше: 1–3 шага.
Не делать: …
Ссылки: план, отчёт, PR.
```

## 6. Гигиена контекста

Всё, что попало в контекст, перечитывается каждым следующим шагом до конца
треда.

- **Искать, а не читать.** `rg -n`, `head`, `sed -n 'a,bp'`, `Read` с
  `offset` и `limit`. Целиком — только файл, который правишь.
- **Тесты.** `pytest -q`; после падения — только упавшие (`--lf`).
- **Git.** Сначала `git diff --stat`, потом диф нужных файлов;
  `git log --oneline -n 10`.
- **Логи CI и сервера** — хвост и поиск (`tail -n 80`, `rg -n "Error|FAILED"`),
  не весь лог.
- **Шаг — это перечитывание.** Независимые команды — в одном шаге:
  параллельными вызовами или одной командой.
- **Не повторять.** Не перечитывать то, что уже видел; не гонять проверку
  снова, если ничего не менялось.
- **Картинки дорогие и остаются в контексте.** Скриншот — когда без него
  нельзя (дизайн, проверка экрана); в браузере — текст страницы вместо снимка.
- **Большой результат** (отчёт, таблица, разбор) — в файл, в чат — 3–5 строк и
  ссылка.
- **Субагент** — когда прочесть надо много, а вернуть мало (поиск по всему
  коду, сбор фактов). Не для того, что тред уже знает: субагент стартует с
  нуля.

## 7. Сообщения и память

- **Каждое сообщение треда попадает к координатору** и остаётся в его
  контексте. Подробно — не значит длинно: что сделано, зачем, что дальше — в
  5–10 строк. Таблицы, логи и разборы — в файл или PR.
- **Память проекта:** `MEMORY.md` — короткие указатели (до ~4 КБ), подробности —
  в отдельных файлах, их читают по надобности. Индекс памяти и инструкции
  проекта лежат в каждом треде.

## 8. Чек-лист координатора перед запуском треда

- [ ] Задача одна, есть критерий «готово».
- [ ] Схема выбрана: один тред или конвейер (§3).
- [ ] Модель и усилие — по роли (§2).
- [ ] Контекст — ссылками на файлы, не пересказом.
- [ ] Тема продолжается — есть «где остановились».
- [ ] Тяжёлое на ПК — по правилам ChatGPT из инструкций проекта.
