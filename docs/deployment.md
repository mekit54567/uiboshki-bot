# Выкладка и сервер

Как код попадает на сервер, как сервер обновляется и что делать, если что-то
пошло не так. Решение и причины — [ADR 0005](adr/0005-safe-deploy.md).

## Схема

```
merge в main → CI (ci.yml) зелёный → deploy.yml двигает ветку deploy
             → сервер раз в минуту видит новый коммит → update.sh
             → копия базы → docker compose up → ждёт /ready → готово или откат
```

- Сервер — VPS в Москве с Ubuntu 24.04: Docker Compose, контейнер бота
  (тот же `Dockerfile`, что в CI) и Caddy, который сам получает HTTPS-сертификат
  для `www.uiboshki.ru`. По голому IP отвечает только `/api/meta`.
- Ветку `deploy` двигает [`deploy.yml`](../.github/workflows/deploy.yml) только
  после зелёного CI мержа. Упал CI, сборка CHANGELOG или PWA — сервер остаётся
  на прошлой сборке.
- Сервер сам тянет ветку из `/opt/kapibara/branch` (по умолчанию `deploy`)
  systemd-таймером раз в минуту (`kapibara-update.timer`). Секретов в GitHub нет.
- [`update.sh`](../deploy/timeweb/update.sh): копия базы `.before-start`,
  запуск новой сборки, до 5 минут ждёт `/ready` с новым коммитом. Не дождался —
  откат на прошлую удачную сборку, коммит помечается плохим, бот пишет старосте.
  Откат кода не откатывает данные: для этого копия `.before-start` и ночные копии.
- Какая сборка сейчас на сервере — `/api/meta` → `build` (короткий хеш,
  номер последнего PR, время сборки и запуска) и шапка `/status` в боте.

## Раскладка на сервере

| Путь | Что там |
|---|---|
| `/opt/kapibara/app` | код (клон репозитория) |
| `/opt/kapibara/.env` | переменные окружения ([configuration.md](configuration.md)) |
| `/opt/kapibara/data` | база SQLite и индекс поиска |
| `/opt/kapibara/branch` | какую ветку тянуть |

Первая установка — [`deploy/timeweb/setup.sh`](../deploy/timeweb/setup.sh)
одной командой: Docker, подкачка, таймер обновления, команда `kap`.

## Команда `kap`

| Команда | Что делает |
|---|---|
| `kap start` / `stop` / `restart` | запустить, остановить, перезапустить бота |
| `kap logs` | логи контейнера (задачи и Telegram, без запросов к веб-приложению) |
| `kap update` | обновиться сейчас, не дожидаясь таймера |
| `kap env` | открыть переменные в редакторе; после правки — `kap restart` |
| `kap check` | какие переменные заданы и работают ([`tools/env_check.py`](../tools/env_check.py)) |
| `kap restore` | забрать базу из копии в S3 ([`tools/s3_restore.py`](../tools/s3_restore.py)) |

Журнал обновлений и откатов: `journalctl -u kapibara-update -n 30`.

## Резервные копии

- Ночью в 04:40 копия базы уходит старосте в Telegram, зашифрованная
  AES-256-GCM (`BACKUP_KEY`); расшифровать без бота —
  [`tools/backup_decrypt.py`](../tools/backup_decrypt.py). Если заданы
  `BACKUP_S3_*`, копия уходит в S3, а не в Telegram.
- Восстановить — `/restore` в боте (прислать файл копии) или `kap restore`.
- Копии хранятся не дольше 30 дней (152-ФЗ).

## Сеть

Сервер в России. Запросы к сервисам за границей (Gemini, OpenRouter) идут
через прокси: контейнер поднимает Xray из `XRAY_CONFIG` и ставит `OUT_PROXY`
([`docker/start.sh`](../docker/start.sh)). Университет, СДО, VK и Яндекс —
напрямую. Новые запросы за границу — только через `net.client()`; проверка
с сервера — `/netcheck` в боте.

## Чего не делать

- Не обновлять Ubuntu до новой версии (`do-release-upgrade`).
- Не запускать второй экземпляр бота на том же токене: Telegram отдаёт
  `Conflict`, и оба бота работают через раз.
- Не давать на сервере команды, которые ждут вставку текста в терминал;
  переменные правятся через `kap env`.

## Мониторинг

`GET /health` — жив ли процесс, `GET /ready` — поднялись ли база, схема и
роутеры. `/status` у старосты — синк СДО, проверка входа, бэкап, индекс
поиска, ИИ и ошибки за сутки; при пяти и больше ошибках за час бот пишет
старосте сам.
