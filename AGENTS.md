## Как общаться и вести задачи

- С владельцем говори по-русски, на «ты». Принимай правки одним сообщением
  в свободной форме. Сам сопоставь пожелания с кодом и проверками.
- Для большой пачки сгруппируй связанные пункты по зависимостям, общим файлам
  и границам PR. Сохрани соответствие исходному списку, чтобы в конце по
  каждому пункту можно было сказать, что сделано, чем проверено или что мешает.
- При параллельной работе ведущий сам формулирует задания субагентам, даёт
  пути к нужным файлам и критерии готовности. Для независимых правок — отдельные
  worktree от согласованной базы (`origin/main` или ветки текущей доработки),
  с непересекающимися зонами изменений. В общий worktree параллельно только
  читают. Ведущий сам собирает изменения и прогоняет общие проверки.
- Субагенты возвращают кратко: файлы и изменения, проверки, открытые вопросы.
  Они не пушат и не меняют общие инструкции, `CHANGELOG.md`, `changelog.d/`
  и `PLAN.md`. Эти файлы ведёт координатор. Вопросы, требующие решения владельца,
  собери в основном чате и продолжи независимые пункты.
- В контекст бери только относящиеся к задаче разделы и фрагменты. Вывод
  поиска, тестов и логов держи коротким. Для длинной задачи сохрани в рабочем
  плане исходный запрос, текущий статус, принятые решения и следующие шаги,
  чтобы можно было продолжить после сжатия контекста или в новом чате.
- Для статуса сверяй актуальные коммиты, PR и [PLAN.md](PLAN.md). Даты и
  версии в старых заметках могут отставать. Ссылки на `/mnt/project-files/`
  ведут в файлы прежнего проекта Claude. Уточняй нужные решения или проси
  нужный файл, если его нет в доступной среде.

## Проект

«Капибара» — неофициальное учебное приложение для студентов РТУ МИРЭА:
расписание, дедлайны и баллы из СДО (Moodle), сдача работ, файлы курсов,
ИИ-ответы по лекциям группы. Клиенты: Telegram-бот [@UiboshkiBot](https://t.me/UiboshkiBot)
с Mini App, PWA (`uiboshki.ru/app`), Flutter для iOS и Android. Установленные
клиенты опираются на контракт `/api/v1` на FastAPI. Бот и API обычно работают
в одном процессе с SQLite, боевой сервер — Docker на VPS Timeweb Cloud.

| Где | Что |
|---|---|
| `bot.py` | Точка входа |
| `kapibara/` | Сервер: `core/`, `features/<раздел>/`, `jobs/`, `bot/`, `ops/` |
| `database/`, `handlers/`, `webapp/` | Прежняя раскладка, код переезжает в `kapibara/` ([ADR 0001](docs/adr/0001-package-layout.md)) |
| `webapp/server.py`, `webapp/routes/` | Приложение FastAPI и маршруты |
| `webapp/static/` | Mini App (`index.html` + `js/`), PWA на HTML (`app-html/`), сайт (`site/`) |
| `app/`, `webapp/flutter/` | Исходники Flutter и сгенерированная запасная веб-сборка (`/app-flutter`) |
| `tests/`, `tools/`, `deploy/`, `channel/`, `design/` | Тесты, скрипты, сервер, посты, дизайн-токены |

Модули в документации местами названы по-старому (`sdo_parser.py`,
`scheduler.py` и т. п.). Актуальные пути — в таблице `MOVED` в
[`tests/test_moved_modules.py`](tests/test_moved_modules.py).

## Локальная среда и проверки

Сервер и CI используют Python 3.12. Ставь зависимости из
`requirements-dev.txt` в изолированное виртуальное окружение. Для тестов
сервера секреты и доступ к боевым сервисам не нужны.

```bash
python3.12 -m venv ../.venvs/uiboshki-bot
source ../.venvs/uiboshki-bot/bin/activate
python -m pip install -r requirements-dev.txt
python -m pytest -q
ruff check .
python tools/check_imports.py
python tools/ratchet.py
PYTHONPATH=. lint-imports
```

Для PWA есть стенд `tools/pwa_html_stand.js` на Playwright/Chromium и ответах
`webapp/static/site/demo.json`. Команды запуска — в начале скрипта. Если
Playwright доступен, а браузер установлен в системе, передай путь в `CHROMIUM`.

Для Flutter используй версию из [CI](.github/workflows/ci.yml) (`3.47.6` на
момент переноса). В `app/`: `flutter pub get`, `flutter analyze`, `flutter test`.
Робот на тех же ответах стенда описан в [.github/workflows/app-robot.yml](.github/workflows/app-robot.yml).
Старый путь `/home/user/sdk/flutter` относится к окружению Claude. Если SDK
не установлен в текущей среде, отмечай, какие проверки остаются за CI.

## Правила разработки

1. Каждое изменение — своя ветка и PR в `main`. Мерж обычным merge commit,
   мержит владелец. Большую новую работу, выходящую за текущую задачу,
   согласуй до начала. Доработки идут в ту же ветку до передачи PR на мерж.
2. Коммиты на русском. `git add` — только конкретных файлов, никогда `-A`.
   Без подписей ИИ, `Co-Authored-By`, ссылок на сессию и «Generated with…».
3. PR открывай готовым к ревью, по [шаблону](.github/pull_request_template.md).
   Отслеживай его CI. При конфликте влей `origin/main` обычным merge и реши
   конфликт. Перед «можно мержить» обнови `origin/main` и проверь
   `git merge-tree --write-tree HEAD origin/main`. В PR, который уже ждёт
   мержа, не пушь новые правки, сделай для них новую ветку.
4. На каждый баг — тест. Хендлеры проверяй через `Dispatcher.feed_update`.
   CI должен быть зелёным до мержа. Храповик только вниз: если долг сократился,
   `python tools/ratchet.py --update` и закоммить `tools/ratchet.json`.
   Новый код без ошибок mypy. Фоновые задачи — через
   `kapibara.core.tasks.spawn`, доступ к Telegram-боту в обработчиках — через
   `kapibara/bot/tg.py`.
5. Обычный PR версию не ставит. Для пользовательских изменений добавь заметку
   `changelog.d/next/<ветка>.md` командой `python tools/changelog.py note`
   (пункты из stdin). Версию и кодовое имя ставит отдельный релизный PR раз
   примерно в 10 PR, номер даёт координатор проекта. `CHANGELOG.md` собирается
   автоматически. После большой задачи коротко обнови «Где мы сейчас» в
   `PLAN.md`. Новое согласованное правило Codex фиксируй здесь.
6. API — в `/api/v1`, JSON без HTML. Существующие маршруты и формат нужны
   уже установленным клиентам. После добавления пути обнови снимок командой
   `python tools/api_snapshot.py`. Группу бери из профиля, рассылки отправляй
   через `delivery.deliver`. Разбор названий файлов и дедлайнов сверяй на
   настоящих данных группы и показывай «было → стало» до применения.
7. Новый способ пользоваться продуктом отражай во всех точках входа по
   [CONTRIBUTING.md](CONTRIBUTING.md) и `tests/test_platforms.py`. При изменении
   README поправь обе языковые версии. Новый экран Flutter перенеси в HTML PWA.
   Файлы дизайн-токенов генерируй из `design/tokens.json` через `tools/tokens.py`.
8. Дизайн: сначала варианты картинками со стенда, потом выбранный вариант.
   Показывай пачками по пять пунктов со скриншотом работающего кода на каждый.
   Новый вид — под `AppStyle.fresh` или `Theme.fresh`, сохраняя прежний.
9. Секреты (токены, куки, ключи, код демо-входа) — в переменных окружения
   сервера. Не проси их в чате и не выводи значения. Изменения настроек
   хостинга, переменных, BotFather, DNS и GitHub сначала объясни владельцу,
   применяет их владелец.

## Ограничения продукта

- Не цитировать тексты песен.
- Не возвращать автопилот с датами в «Цели по предмету».
- Не менять идентификатор `ru.uiboshki.app`.
- Не упоминать оплату, цены и «Капибару+» в iOS-сборке и её листинге.
- При живом тесте Telegram используй только бот и каналы проекта, вход по QR.
  Чужие чаты, номер телефона и коды не использовать.
