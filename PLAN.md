# План развития УИБО-БОТ

Черновик для себя (Claude) на следующую сессию, когда появится пуш через комп владельца.
Владелец дал добро добавлять свои идеи без согласования — если что-то не зайдёт, откатываем, не страшно.
Порядок ниже — предлагаемый приоритет, не жёсткий контракт: смещать по ходу дела нормально.

## Фаза 0 — фиксы, которые не требуют архитектурных решений

Можно делать в первую же сессию с пушем, риска нет, эффект сразу.

- [ ] `handlers/files.py`: `handle_sync_json` (`@router.message(F.document)`) перехватывает документы
      в любом FSM-состоянии, включая `HWAdd.content` из `announce.py`. Добавить
      `StateFilter(None)` или явную проверку `state.get_state() is not None: return` в начале.
      Баг: `/addhw` с прикреплённым файлом молча не срабатывает.
- [ ] Единый набор кнопок главного меню (сейчас размазан по `start.py`, `deadlines.py`, `files.py`,
      `solver.py` как локальные `MAIN_KB`/`BUTTON_TEXTS`, местами неполный — в `solver.py`
      `BUTTON_TEXTS` не хватает "📝 ДЗ", "🏆 Рейтинг", "⋯ Действия"). Вынести `MAIN_KB` и
      `MENU_BUTTON_TEXTS` в отдельный `keyboards.py`, и добавить общий guard на все FSM-состояния:
      если входящий текст — это текст кнопки меню, а не ожидаемый ввод, сбрасывать state и
      обрабатывать как обычную команду, а не глотать как значение поля.
- [ ] `STAROSTA_ID` — при `STAROSTA_ID == 0` сейчас все admin-команды (`/announce`, `/setzam`,
      `/importdeadlines`, `/syncfiles`) открыты всем. Либо падать при старте, если переменная не
      задана, либо явно логать warning уровня critical при `init`.
- [ ] `database.py`: при старте выставить `PRAGMA journal_mode=WAL;` — снижает риск
      `database is locked` при параллельных cron-джобах (scheduler.py гоняет 3 job'а) + хендлерах.
- [ ] `schedule_parser.fetch_schedule_raw()` дергается без кэша отовсюду (каждую минуту из
      `check_lesson_reminders`, плюс из каждой команды). Добавить простой TTL-кэш (5–10 минут) —
      разгружает и бота, и стороннего провайдера ical.
- [ ] Мёртвый `GROQ_MODEL` в `config.py` — не используется, `groq_solver.py` хардкодит свои
      модели напрямую. Убрать или реально прокинуть.

## Фаза 1 — смена интерфейса: от дерева клавиатур к свободному вводу

Идея: держать текущие команды/кнопки как fallback, но дать основной путь через
естественный язык поверх уже существующего Groq-клиента.

- [ ] Маленький intent-роутер: короткий системный промпт классифицирует свободный текст
      в один из существующих обработчиков (расписание/дедлайны/файлы/решить/ДЗ/голосование)
      + извлекает параметры (дата, предмет). Один дешёвый вызов перед основной логикой.
  Fallback — если классификатор не уверен, гонит в решалку как раньше (`handle_plain_text`).
- [ ] Постепенно убирать жёсткие FSM-цепочки там, где это не критично (добавление дедлайна,
      выбор предмета для решателя) — заменять на разбор одной фразой ("добавь дедлайн по
      матстату на 30.05 сдача лабы").
- [ ] Не трогать FSM там, где нужен строгий пошаговый ввод (загрузка файла с бинарным вложением).

## Фаза 2 — killer feature: анонимная лента группы

Главная гипотеза сессии: то, чего не хватает — не улучшение утилити-функций, а социальный
слой, который дают открывать бота без повода (см. кейс "Кампус" — анонимная лента = 40% DAU).

- [ ] Новая таблица `feed_posts` (id, text, photo_file_id, author_id — не показывается,
      created_at, reply_count).
- [ ] `/anon` (или новая команда `/feed`/`⋯ Подслушано`) — пишет не старосте лично,
      а постит анонимно в общий чат группы (нужен `chat_id` группы в конфиге,
      не только `STAROSTA_ID`).
- [ ] Реакции/комменты — через reply в Telegram на пост бота, либо через inline-кнопки
      👍/😂/🔥 с счётчиком в БД.
- [ ] Продумать анти-спам/модерацию — простая: rate-limit 1 пост в N минут на юзера,
      плюс возможность старосты удалить пост (`/delpost ID` или кнопка).
- [ ] Оставить старый приватный `/anon → старосте` как отдельную опцию — не всё должно быть
      публичным (жалобы конкретно старосте лично).

## Фаза 3 — расписание как источник правды, а не просто вывод

- [ ] Диффы расписания: хранить снепшот последнего распарсенного ical (или хотя бы
      ключевых полей per день), сравнивать при каждом фетче, слать пуш только при изменении
      (перенос аудитории/времени/отмена пары). Использовать уже существующий кэш из Фазы 0.
- [ ] Заметки на конкретную пару: таблица `lesson_notes` (subject, date, text/file_id,
      created_by) — привязка не к дедлайну "вообще", а к конкретному занятию в расписании,
      выводить прямо под парой в `/today`.

## Фаза 4 — СДО и внешние данные (требует ручной разведки перед кодом)

- [ ] Авторизация СДО идёт через SSO `login.mirea.ru` (OAuth2, `client_id` + redirect на
      `online-edu.mirea.ru`) — не простая Moodle-форма. Прежде чем писать код: руками пройти
      логин с открытым DevTools/Network, проверить — есть ли капча/CSRF-токен на форме.
      Если чистый POST username+password без капчи — реально сделать авто-релогин по
      сохранённым (зашифрованным) кредам вместо протухающих куки.
  Если капча — fallback на "раз в несколько дней попросить хозяина аккаунта обновить сессию".
- [ ] Как будет ясен механизм логина — писать сам парсер: тянуть задания/файлы,
      диффать с уже сохранёнными, автодобавлять новые дедлайны/файлы.
- [ ] Поиск преподавателей/аудиторий — не парсить с нуля, посмотреть исходники
      `mirea-ninja/mirea-teacher-schedule-bot` (свежий, не архивный, в отличие от
      `rtu-mirea-schedule`) на источник данных, по возможности переиспользовать.

## Фаза 5 — решалка

- [ ] Добавить DeepSeek как альтернативный backend (дешёвый API, ~30–40% группы и так на
      бесплатном DeepSeek). Разница с "просто вставить в чат самому" — контекст: решала должен
      видеть доску ДЗ/дедлайн, к которому привязана задача, и историю по этому заданию —
      это то, что голый чат-бот без интеграции дать не может.
- [ ] Выбор модели — либо явной командой/кнопкой, либо через тот же intent-роутер
      ("реши через дипсик: ...").

## Фаза 6 — по возможности, не приоритет

- [ ] FTS5-поиск по файлам (title+subject+теги) — актуально станет, когда файлов много.
- [ ] Слияние таблиц `deadlines` и `homework` в одну сущность — сейчас две параллельные
      системы одного и того же смысла ("что сдать к дате"), разделены по историческим причинам
      (староста/зам), это усложняет и код, и восприятие.
- [ ] Telegram WebApp для расписания/файлов вместо чат-сообщений с инлайн-кнопками — самая
      дорогая по трудозатратам идея, но даёт реальный визуальный отрыв от нативных приложений.
